# Backend testing and troubleshooting

Use synthetic data and a disposable project for checks that write to Supabase.
Never commit credentials or connection strings. Local database tests simulate
Supabase identity and do not replace testing against hosted authentication.

## Local database checks

With the project's supported Node version and dependencies installed, run:

```sh
npm test -- tests/backend/database.test.ts
```

These tests apply the migrations to an in-process PostgreSQL database and check
constraints, grants and row-level security. For other backend tests, run
`npm test -- tests/backend`. Failures involving denied access can indicate missing
migrations, incorrect grants or policies, or a mismatched authenticated user.

The SQL smoke script can also run against an already migrated disposable test
database using an owner connection supplied locally:

```sh
psql "$NEWTON_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/learning_foundation.sql
```

Apply migrations in filename order to a new database. For an existing project,
inspect its schema and migration history first; do not blindly rerun migrations
that create existing tables. Never point the smoke script at a production database.

## Hosted authentication and isolation checks

The opt-in hosted suite checks real authentication, account ownership and
history against a disposable Supabase project and a locally running app. It does
not test Google consent or call voice and vision providers. Its project guard
restricts the suite to the configured test project; the app URL must be loopback.

Create an ignored `.env.hosted-test.local` with credentials for two distinct
disposable accounts. Keep it private and use appropriate file permissions:

```dotenv
NEWTON_TEST_EMAIL_A=
NEWTON_TEST_PASSWORD_A=
NEWTON_TEST_EMAIL_B=
NEWTON_TEST_PASSWORD_B=
```

Configure the project URL and publishable key in the ignored `.env.local`.
The test fixtures use password authentication through the Supabase SDK; the
application's Google sign-in is tested separately. Run the production build
locally, then start the suite in another terminal:

```sh
npm run build
npm run start -- --hostname 127.0.0.1 --port 3107
# In a separate terminal:
npm run test:hosted
```

The browser portion requires the matching Playwright Chromium installation.
The suite creates synthetic records; some append-only records may remain for an
administrator to clean up. Do not remove accounts containing wanted data.

## Troubleshooting

- **401 or sign-in failure:** verify the test account, enabled auth provider and
  local environment settings. Follow the [Google setup guide](google-auth.md)
  when checking the user-facing sign-in flow.
- **403 or cross-origin failure:** open the app at its configured origin and
  check that its local URL and request origin match.
- **404 for a session:** confirm it exists and belongs to the signed-in user;
  another user's session must remain inaccessible.
- **Database or history unavailable:** check migration history, table grants,
  RLS policies and the project's status before retrying.
- **Unexpected data access:** stop testing with real information and verify
  ownership policies using two separate synthetic accounts. RLS isolates users;
  it does not prove that self-owned learning evidence was generated by the tutor.
- **Browser test cannot start:** install the browser version required by the
  project's Playwright dependency, then retry the affected test.

Review deployment controls and provider data handling separately before using
real student data. Local and mocked tests cannot establish production readiness.
